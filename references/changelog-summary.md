## 破壊的変更・非推奨の履歴

| 時期 | 内容 | 影響と対処 |
| --- | --- | --- |
| `0.7.x`（2026-04-16 頃） | `--ai` を `--integration` に置換（非推奨化） | ドキュメントも全面置換済み |
| `0.8.2`（2026-04-28） | `--no-git` を非推奨化。`0.10.0` での廃止を予告 | 予告期間は約 6 週間 |
| **`0.10.0`（2026-06-09）** | `--ai` / `--ai-commands-dir` / `--ai-skills` を**削除**。`--no-git` を削除し、**git 拡張をオプトイン化** | 既定で Git ブランチ運用が無くなった。必要な場合は `specify extension add git` |
| `0.12.3`（2026-07-01） | Copilot の skills 既定化を事前警告 | `0.16.0` で実施 |
| PR #3790（`0.13`〜`0.14` 期） | `/constitution` がテンプレート群へ伝播しなくなる | 公式見解は「破壊的変更ではない」。ランタイム解決（`plan` / `tasks` / `analyze` が constitution を毎回読む）が本来の設計であり、旧挙動が必要な場合は `constitution-sync` プリセットで復元 |

`0.10.0` は事実上の設計転換点です。**Git 依存を core から切り離し、アクティブ機能の決定を `.specify/feature.json` に移した**ことで、Git を使わない運用や Git 以外の VCS でも Spec Kit が成立するようになりました。

## 機能追加の傾向分析

1. **エージェント統合の追加が最大の量を占める**。40 件以上の統合追加が全期間に分散しています。特定エージェントへのロックインを避けるという設計方針が、そのまま変更履歴の形に現れています。
2. **抽象化のレイヤーが年間で 4 段重ねられた**。拡張（2026-02）→ プリセット（2026-03）→ ワークフロー（2026-04）→ ステップカタログ／バンドル（2026-06）。各層は前の層を置き換えるのではなく積み上げられており、既存プロジェクトが取り残されにくい構造です。
3. **セキュリティ関連の修正が 1.0 前後で急増**。`fix(bundler): reject ...` / `fix(presets): fail closed on ...` / `fix(auth): reject malformed URL ports` など、カタログ経由の外部コード取り込みに対する入力検証の強化が集中しています。フェイルクローズ（不正入力時は安全側に倒す）方針が徹底されつつあります。
4. **スクリプトの Python 移植が 2026-07 に完了**。Bash / PowerShell / Python の 3 系統が揃い、`--script py` が選択可能になりました。Python を主力とする組織にとって、スクリプト層の可読性・改変容易性が向上しています。
5. **GitHub Actions 上のラベル駆動エージェンティックワークフローが 2026-07 以降に整備**。`bug-assess` / `bug-fix` / `bug-test` / `feature-assess` の 4 種が `.github/workflows/*.md` として定義され、`.lock.yml` にコンパイルされる方式です。これは Spec Kit 本体の機能ではなく**リポジトリ運用のリファレンス実装**である点に注意が必要です。

## バージョン互換性の方針

公式ドキュメント（`docs/upgrade.md`）は「メジャーリリースについてセマンティックバージョニングに従う。CLI とプロジェクトファイルは同一メジャーバージョン内で互換」と記載しています。推奨実務は CLI とプロジェクトファイルを同時に更新することです。

拡張・プリセットは各マニフェストで `requires.speckit_version` により互換範囲を宣言します（例：`adrkit` は `>=0.13.0,<0.16.0`）。したがって**コア更新によりコミュニティ拡張が非互換になる事象は構造的に起こり得ます**。導入時は依存する拡張の対応バージョン幅を確認する必要があります。
