# イクシス受託開発への適合性評価

## イクシス開発スタイル

- 小規模システムの上流～下流一貫担当
- パートナー建設会社との協働
- 測量新技術の原理試作（トンネル工事、橋梁工事、物流倉庫）
- AWS、C++、Python、Streamlit、FastAPI を使用
- 行列計算・画像処理・点群処理が中心領域
- 社内ツールの開発・運用も担当

---

## Spec Kit の適合性

### 合致する点

#### 1. 上流～下流一貫担当との親和性

Spec Kit の 9 コマンドは、要件定義から実装・収束確認までを 1 人が通しで扱う前提の設計です。工程間の引き継ぎ文書を作るのではなく、**同一人物が同一の成果物集合を段階的に詳細化する**構造であり、一貫担当のスタイルとそのまま重なります。

`spec.md`（何を・なぜ）と `plan.md`（どう作るか）が分離されている点も有効です。顧客と合意すべき内容が `spec.md` に、技術判断が `plan.md` に自然に分かれます。

#### 2. 成功基準の技術非依存・測定可能性

仕様テンプレートは Success Criteria を「**技術非依存かつ測定可能**」であることを要求します。測量新技術の原理試作では、この形式が要求仕様の言語化に直接使えます。

```text
SC-001: 点群 1 億点に対する平面抽出を 5 分以内に完了する
SC-002: 標定点 5 点における位置誤差の RMS が 10 mm 以内
SC-003: 現場作業員が計測開始から結果表示まで 3 タップで到達できる
```

「使用ライブラリ」や「アルゴリズム名」ではなく達成すべき数値で書かせる強制力があるため、パートナー建設会社との合意形成に適した文書が生まれます。

#### 3. Git 非依存（0.10.0 以降）

アクティブ機能の決定は `.specify/feature.json` であり、Git は `git` 拡張としてオプトインです。パートナー企業との協働で Git 運用が確立していない場合や、顧客側リポジトリの運用ルールを変えられない場合でも、Spec Kit 自体は導入できます。

#### 4. Python 中心の技術構成

- CLI 本体が Python 3.11+ で書かれており、内部を読んで理解・改変できます
- スクリプト層に `--script py` の選択肢があり（0.12.4 以降）、Bash / PowerShell を経由せず Python で完結できます
- 主力言語が Python である組織にとって、スクリプト層の改変障壁が低い構成です

#### 5. エアギャップ・オフライン導入

`specify init` はネットワーク不要（コアパックが wheel に埋め込み済み、0.4.0 以降）。現場作業やセキュリティ制約の厳しい顧客環境でも導入経路があります。認証もオプトインで、設定しない限り一切の外部通信認証を行いません。

#### 6. カスタマイズ機構がプロセスの置換まで届く

プリセットの `wrap` / `append` 戦略により、コアの指示を保持したまま建設分野固有のセクション（計測条件、現場環境、安全要件、精度検証）を仕様テンプレートに追加できます。コアの更新に追随しやすい形でカスタマイズできる点が重要です。

#### 7. 小規模チームでの学習コスト

日常的に使うのは 5 コマンド（`specify` / `plan` / `tasks` / `implement` / `converge`）です。公式が「短経路」を先に提示している構成は、少人数の受託チームに適しています。

### 課題となる可能性がある点

#### 1. 原理試作と仕様先行の思想的な衝突（最大の論点）

Spec Kit の中核思想は「作る前に何を作るかを定義する」ことです。一方、測量新技術の原理試作は「作って計測してみないと要件が確定しない」性質を持ちます。

**この衝突は緩和可能です。** 公式が定義する 3 つの永続化モデルのうち **Flow-back Spec**（実装からの発見が成果物を再形成することを許容し、後で整合させる）が原理試作に適合します。公式も「実装での発見が当初計画を作り変えることが想定される場合」に flow-back を推奨しています。

ただし公式が指摘するリスク（silent drift：下位成果物だけ変えて `spec.md` に反映せず、後の担当者がどれを信じるべきか分からなくなる）は現実的です。**「試作サイクル終了時に `spec.md` を実態へ追随させる」チェックポイントを運用ルールとして定める必要があります。**

もう 1 つの現実的な選択は、**原理試作フェーズには Spec Kit を使わず、方式が固まってから製品化フェーズで導入する**という段階分けです。公式の Development Phases でいう Creative Exploration（並行実装の比較）は Spec Kit の想定範囲ですが、そこでの利得は本番機能ほど大きくありません。

#### 2. C++ プロジェクトでの実績が不明

公式の community walkthroughs は .NET / Java / Go / Spring Boot / React の事例のみで、**C++ の事例はありません**。

Spec Kit 自体は言語非依存です（テンプレートの Technical Context は「Python 3.11, Swift 5.9, Rust 1.75」を例示、Project Type も自由記述）。しかし次の点は未知数です。

- ビルドシステム（CMake）やヘッダ／ソース分離を前提としたタスク分解の質
- テンプレートの Project Structure が `src/models/`, `src/services/` という Web 寄りの構成を例示している点
- 数値計算・点群処理のような**アルゴリズム中心のタスク**が、ファイルパス単位のタスク分解と噛み合うか

`plan-template.md` の Project Structure は「Option 1/2/3 を削除し、実際のレイアウトへ置換せよ」という指示付きのため、C++ 構成への適応自体は可能です。ただし**プリセットで C++ 向けの Project Structure 例を用意する**のが実務上は必要と判断します。

#### 3. Streamlit / FastAPI の小規模システムでの費用対効果

9 コマンド（短経路でも 5 コマンド）のプロセスは、数百行規模の社内ツールに対しては重すぎます。Spec Kit 自身も「小規模機能には短経路」と案内していますが、それでも `spec.md` / `plan.md` / `tasks.md` の 3 ファイルが生成されます。

同梱の **`lean` プリセット**（0.6.1 以降、最小構成のワークフローコマンド）が緩和策として存在します。導入時に評価対象とすべきです。

#### 4. Issue 連携の粒度

`/speckit.taskstoissues` は **1 タスク 1 Issue** です。30 タスクの機能なら 30 Issue が生成されます。小規模案件でこの粒度は現実的ではありません。プリセットによる上書き（ユーザーストーリー単位・フェーズ単位への集約）が事実上必須です。

#### 5. コミュニティ拡張の信頼性

Issue 連携・CI ゲート・ブラウンフィールド支援など、有用な機能の多くがコミュニティ拡張にあります。**すべて `verified: false` であり、GitHub による監査・推奨・サポートはありません。** 顧客環境へ持ち込む場合、コード確認の責任は自社にあります。

#### 6. ワークフローの `shell` ステップにサンドボックスが無い

AWS の認証情報を持つ環境でワークフローを走らせる場合、`{{ }}` の単純文字列置換によるシェルインジェクションが現実的なリスクになります。公式も明示的に警告しています。**デプロイ先・環境名は必ず `enum` で制約する**規約が必要です。

#### 7. リリースブランチ戦略への非対応

`git` 拡張は機能ブランチのみを扱い、リリースブランチ・タグ・バージョニングの概念を持ちません。顧客への納品バージョン管理は Spec Kit の外側で行うことになります。

#### 8. 顧客リポジトリへの `.specify/` 追加に関する合意

受託開発では顧客リポジトリに `.specify/` と `specs/` が追加されます。成果物の帰属、レビュー負担、納品後の保守について**事前合意が必要**です。公式の「`init` 差分をレビュー可能な状態で提示する」手順は、この合意形成の材料としてそのまま使えます。

### カスタマイズが必要な範囲

| 対象 | 手段 | 優先度 |
| --- | --- | --- |
| 仕様テンプレートへの計測条件・精度要件・現場環境セクション追加 | プリセット（`append` または `wrap`） | 高 |
| Project Structure の C++ / Python 混在構成例 | プリセット（`plan-template.md` の置換） | 高 |
| Issue 粒度をユーザーストーリー単位へ集約 | プリセット（`speckit.taskstoissues` の上書き） | 高 |
| constitution の社内標準版（AWS 構成、コーディング規約、点群処理の精度基準） | プリセット または テンプレート化した雛形 | 中 |
| 小規模案件向けの軽量プロセス | 同梱 `lean` プリセットの評価 | 中 |
| 社内カタログの構築（配布統制） | `specify extension catalog add <自社 URL>` | 中 |
| CI ゲート（仕様ドリフト検知） | `ci-guard` の評価、または自前実装 | 低 |

## 推奨導入シナリオ

### 前提

**段階を分け、リスクの低いところから始めます。** 受託案件へ直接持ち込まず、社内ツールで手順とプリセットを固めてから展開する順序を推奨します。

### フェーズ 1：社内ツールでの検証（1〜2 か月）

**対象**: 社内ツール 1 件、Streamlit または FastAPI の小規模システム

1. `uv tool install specify-cli` で導入。`specify init --here --force --integration claude`
2. `git` 拡張は導入せず、既存のブランチ運用のまま検証する
3. 短経路（`specify → plan → tasks → implement → converge`）で 1 機能を通す
4. `lean` プリセットの有無で成果物量を比較する
5. 評価項目
   - `spec.md` の記述が顧客説明に使える水準か
   - `tasks.md` の粒度が実作業と噛み合うか
   - `converge` の収束判定が実感と一致するか
   - 全体の所要時間が、従来手法と比べて許容範囲か

**判断基準**: 従来手法に対して所要時間が 1.5 倍以内に収まり、かつ成果物が顧客説明に流用できるなら次へ進みます。

### フェーズ 2：社内標準プリセットの作成（1 か月）

フェーズ 1 の知見を基に、自社プリセットを 1 つ作ります。

- 仕様テンプレートへ「計測条件」「精度要件」「現場環境・安全要件」セクションを `append` で追加
- `plan-template.md` の Project Structure を C++（CMake）／Python（パッケージ）／AWS 構成の 3 案へ置換
- `speckit.taskstoissues` をユーザーストーリー単位の Issue 生成へ上書き
- constitution の雛形を社内標準として用意（AWS 構成方針、テスト方針、精度検証方針）

配布は社内カタログ（`catalog.json` を社内 Git または S3 でホスト）で行い、公式カタログは `discovery-only` に設定します。

**成果物**: プリセット 1 件 + 導入手順書。これが受託案件へ持ち込む単位になります。

### フェーズ 3：受託案件への適用（案件 1 件で試行）

**選定基準**: 次の条件を満たす案件を選びます。

- 要件が比較的固まっている（原理試作ではなく、方式が確定した製品化フェーズ）
- 顧客が GitHub を使っている、または成果物の Markdown 納品を受け入れる
- 期間に多少の余裕がある

**適用範囲**: 全工程ではなく、**境界の明確な機能 1 件**から始めます（公式の既存プロジェクトガイドと同じ方針）。

**Issue 連携**: フェーズ 2 のプリセットでストーリー単位の Issue を生成し、GitHub Projects へは Projects 側の自動化ルール（Issue 作成時に自動追加）で接続します。コミュニティ拡張の導入は、必要性が確認されるまで見送ります。

### フェーズ 4：原理試作への適用可否の判断

フェーズ 1〜3 の知見を踏まえて判断します。現時点の見立ては次のとおりです。

| 案件種別 | 適用可否 | 永続化モデル |
| --- | --- | --- |
| 社内ツール開発 | 適用可 | Living Spec（`spec.md` を契約とし下流を再生成） |
| 受託・製品化フェーズ | 適用可 | Flow-forward Spec（機能ごとに不変の履歴を残す。納品物として有効） |
| 受託・原理試作フェーズ | **条件付き** | Flow-back Spec（実装からの逆流を許容。試作サイクル末に `spec.md` を追随させるルールが必須） |
| 極小規模のスクリプト | 非推奨 | — |

### 適用しない判断も選択肢

原理試作フェーズについては、**Spec Kit を使わず従来手法で進め、方式確定後に `/speckit.specify` で仕様を起こす**という運用も合理的です。この場合 Spec Kit は「試作の成果を製品仕様へ翻訳する道具」として機能し、思想的な衝突を回避できます。

## 総合評価

| 観点 | 評価 | 根拠 |
| --- | --- | --- |
| 技術的な導入障壁 | **低** | Python 製、MIT、オフライン導入可、Git 非依存 |
| 既存プロジェクトへの導入 | **中** | 公式ガイドが整備されている。`--force` の差分レビューが必須 |
| 一貫担当スタイルとの適合 | **高** | 上流から下流までを同一成果物集合で扱う設計 |
| 原理試作との適合 | **中** | 思想的衝突がある。Flow-back モデルと運用ルールで緩和可能 |
| C++ 案件での実績 | **不明** | 公式事例なし。プリセットでの補完が前提 |
| Issue 連携の即戦力性 | **低** | 粒度が細かすぎる。プリセットによる上書きが事実上必須 |
| 保守追随の容易さ | **高** | プリセットによるカスタマイズはコア更新に追随しやすい |
| 顧客環境への持ち込み | **中** | `.specify/` 追加の事前合意が必要。エアギャップ導入は可能 |

**結論**: 社内ツールと受託の製品化フェーズには適用価値があります。原理試作フェーズへの適用は、永続化モデルの選択と運用ルールの整備を前提とした条件付きです。導入は社内ツールから段階的に進め、自社プリセットを固めてから受託案件へ展開する順序を推奨します。
